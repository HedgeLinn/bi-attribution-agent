# BI 归因对话 Agent — 项目方案

> 最后更新:2026-09-09

## 一、目标

构建一个 **BI 场景的分析型对话 agent**:不仅能查数据,更能**主动发现问题 → 提出假设 → 下钻维度定位根因**。

不是 Text2SQL(用户输入筛选维度→查数,单轮被动),而是**归因分析闭环**(异常检测→贡献度下钻→根因定位,多轮假设-验证)。

## 二、范式对比

| | 查数 agent(旧范式) | 归因 agent(本项目) |
|---|---|---|
| 触发 | 用户说「查XX维度XX指标」 | 系统发现异常,或用户问「为什么下滑」 |
| 模型角色 | 翻译(意图→SQL) | 分析师(提假设→验证→下钻) |
| 循环 | 单轮 | 多轮假设-验证 |
| 产物 | 一张表 | 带证据链的根因结论 |
| 难点 | SQL 准确率 | 语义层 + 归因算法 + 假设质量 |

## 三、归因 loop(核心流程)

```
用户:"为什么 GMV 下滑?"
  → [异常检测] 确认异常:GMV 环比 -15%
  → [假设生成] LLM 提假设:H1 某地区掉量 / H2 客单价降 / H3 某品类断货
  → [贡献度下钻] 对假设维度算贡献度,取 top-k 切片
  → [验证/排除] 是华东?下钻华东→是上海?下钻上海→是某门店?
  → [根因确认] 证据链完整
  → [结构化输出] 结论 + 证据链 + 建议
```

关键认知:**归因 agent 的增量价值是「决定下钻哪个维度」,不是「把问题翻译成查询」。**

## 四、技术选型

| 层次 | 选择 | 理由 |
|------|------|------|
| 数据引擎 | DuckDB | 嵌入式、零部署、分析型聚合秒级 |
| 数据来源 | 自造示例数据(带下钻层级) | 无数据基础,先闭环 |
| 语义层 | 自建 YAML 字典 | 归因地基,也是学习目标 |
| 归因引擎 | 自写贡献度下钻 | 无成熟开箱库,10-20 行 |
| LLM harness | 手写最小 loop | 阶段 0-1 刻意练习 |
| 模型 | new-api.mypy.cn + deepseek-v4-pro | 已配置 |
| 记账 | llm_cost 回调 | 已配置 |
| 前端 | Streamlit | 几分钟出 demo |

排除:cube.dev/dbt semantic layer(太重)、LangChain/LangGraph(现在上遮蔽原理)、ClickHouse/StarRocks(要部署运维)。

## 五、构建分工(3 子 agent + 主线)

| 角色 | 职责 | 依赖 |
|------|------|------|
| 子 agent A | 造数据 + 语义层 | 无,先做 |
| 子 agent B | 归因引擎(贡献度下钻) | A 的接口契约 |
| 子 agent C | Streamlit 前端 | B + 主线的输出契约 |
| 主线(我) | harness 核心 loop + 模型接入 + 组装 | A、B |

执行顺序:`A(契约) → B 与主线并行 → 组装 → C`。

拆分原则:强耦合合并(数据+语义层同一 agent)、学习目标不外包(harness 我亲自写)、边界干净的可并行(归因引擎)。

## 六、目录规划

```
chatv2/
  docs/            # 方案与 schema 文档
    PLAN.md
    DATA_SCHEMA.md
  data/            # 生成的数据(duckdb 文件 / parquet / csv)
  scripts/         # 造数脚本
  semantic/        # 语义层 YAML
  attribution/     # 归因引擎
  harness/         # agent loop + 模型接入
  app/             # Streamlit 前端
```

## 七、里程碑

1. 数据 + 语义层就绪(子 agent A)
2. 归因引擎跑通贡献度下钻(子 agent B)
3. harness 主线串起「问→下钻→结论」(我)
4. Streamlit 前端套壳(子 agent C)
